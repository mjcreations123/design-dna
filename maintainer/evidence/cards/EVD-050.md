# A project design record is useful only when it describes this project

## Claim

A maintained design record can preserve atmosphere, semantic colors,
typography, component states, layout, depth, media, responsive behavior, and
traceable do or do-not rules for future editors.

## Observation

The pinned MIT-licensed Awesome DESIGN.md repository demonstrates a broad,
readable design-spec schema through named brand records and previews.

## Scope and limitations

The records include reverse-engineered proprietary identities. Repository
licensing does not grant rights to copy trademarks, fonts, trade dress, or
another company's visual language. A fixed section inventory also becomes
paperwork when a small handoff or existing source already serves the need.

## Counterexamples

A single-page handoff may need no DESIGN.md; a monochrome system has no accent
budget; a project can use several shape families or no tokenized radius rule;
an existing Storybook or design-system repository can be authoritative.

## Positive action

Keep DESIGN.md optional, delete irrelevant sections, and derive retained rules
from the accepted build and owner sources. Never start from another brand's
record.

## Supports

`RISK-SYS-001`, `RISK-REPEAT-001`

## Validation

Review a transferred project with and without a new DESIGN.md. Confirm that any
record matches shipped tokens and states and carries no invented accent, radius,
motion, or rule-count requirement.

## Retention

Pinned public community repository evidence. Review within 90 days and retain
the third-party identity boundary.
