# Current Web Vitals thresholds are diagnostics, not invented project budgets

## Claim

When a project has no approved performance target, current official Core Web
Vitals thresholds can orient diagnosis only if they are dated, reverified, and
kept distinct from field evidence and owner-approved budgets.

## Observation

Current official guidance defines good field results at the 75th percentile as
LCP at or below 2.5 seconds, INP at or below 200 milliseconds, and CLS at or
below 0.1.

## Scope and limitations

Metrics and thresholds can change. These are field percentile definitions, not
a claim that one lab run represents real users or that every project has the
same performance risk and contract.

## Counterexamples

A high-risk interaction may need a stricter target. A local concept can use
provisional diagnostics without any production claim. An owner-approved SLA or
representative-user need supersedes a generic diagnostic.

## Positive action

Use approved targets first. Otherwise record the current threshold source and
date, label it diagnostic, measure production-like conditions, distinguish lab
and field evidence, and propose a project budget for accountable review.

## Supports

`RISK-UX-001`, `RISK-CODE-001`

## Validation

Performance records identify route, build, browser, device, network, cache,
method, field-versus-lab status, and date; no single synthetic score becomes a
readiness claim.

## Retention

Current public official guidance. Review within 90 days because metrics and
threshold definitions can change.
